Working plan · 2026-08 · 구현 전

현재 Q-SEED를 신뢰할 수 있게 만들기

기능은 이미 Phase 1–4까지 있다. 문제는 “이 숫자·이 명령을 다시 돌리면 같은 이야기가 나오는가”다. 이번 단계는 새 전략이 아니라, 검증·재현·문서·설치를 한 줄로 잇는 일이다. 파일 정리는 후순위.

이번 단계
  • GitHub Actions가 린트만이 아니라 테스트를 돌리게
  • 백테스트 결과가 코드 버전·데이터 스냅샷과 같이 남게
  • 케이스 스터디 숫자와 산출물 경로가 코드와 맞게
  • dbt가 설명만이 아니라 깨지면 실패하는 테스트를 갖게
  • 클론 → 설치 → 확인이 문서대로 끝나게
미룸
  • 미사용 파일 삭제 (metrics_calc.sql 등)
  • 의존성 다이어트 (PySpark, Jupyter…)
  • Hosted API / 공개 데모
  • CLI subcommand 재설계
이 HTML은 브레인스토밍용이다. 코드 변경은 아직 없다. 아래 권장안을 고르거나 바꾸면, 그다음 PR에서 한 줄씩 구현한다.

지금 상태 — 무엇이 약한가

영역 있는 것 없는 것 / 어긋난 것
CI .github/workflows/lint.yml — pre-commit (ruff, mypy, prettier) pytest 없음 · dbt parse/test 없음 · uv sync가 Spark·Jupyter까지 끌어 CI가 무거움
재현성 uv.lock, 백테스트 manifest.json (시장·전략·지표) git SHA · dirty 여부 · 패키지 버전 · DuckDB fingerprint 없음. yfinance 라이브 수집은 비트 단위로 다시 만들 수 없음
문서 수치 2026-07 KR 케이스 스터디 3편 Phase 3 reversal_5d와 Phase 4 equal_weight가 “동일 조건”인데 숫자가 다름. 산출물 경로도 코드와 불일치
dbt stocks/market 모델, 짧은 schema.yml 테스트는 dim_stocks__security의 not_null 3개뿐. dbt/tests/ 없음. CI에서 안 돈다
설치 make setup, Docker, getting-started clone URL이 플레이스홀더. 설치 후 스모크가 --help뿐. CLI 표기가 uv run qseed / python -m src.qseed.cli로 섞임. Docker 포트 8080 vs 웹 8000 / Streamlit 8501
단위 테스트 합성 데이터 pytest 6파일 (보안 메타, gap, IC, 시장 지표 등) 백테스트 엔진·manifest 회귀가 거의 없음. CI가 돌리지 않아 로컬에서만 지켜짐

백테스트 문서 수치 — 가장 눈에 띄는 균열

두 문서 모두 KOSPI·KOSDAQ / reversal_5d / 롱숏 / 21일 리밸런싱이라고 적혀 있다. Phase 4는 “Phase 3와 동일한 조건”이라고 명시한다.

Phase 3 백테스트 Phase 4 equal_weight
CAGR +0.32% +7.63%
MDD −61.7% −39.6%
Sharpe +0.12 +0.47
문서가 가리키는 파일 backtest_summary.json optimize_summary.json
코드가 실제로 쓰는 파일 runs_index.json + {run_id}/manifest.json + summary.parquet
코드상 equal_weight는 opt_max_assets=50 상한을 타지 않는다. 엔진이 최적화 메서드일 때만 종목을 자른다. 그래서 “50종목 제한 때문에 숫자가 갈렸다”는 1순위 가설이 아니다.

가설 (검증 전에 단정하지 말 것)

A. 데이터 빈티지가 다르다

2026-07 문서와 이후 DB 갱신이 섞였거나, 기간·유니버스가 로그에만 있고 문서에 없다.

B. 손복사

가리키는 JSON 파일이 코드에 존재하지 않는다. 숫자를 로그에서 옮긴 뒤 경로를 추정했을 가능성이 크다.

C. 실행 플래그가 미묘하게 다름

비용, 날짜 필터, 시장 목록, 초기 자본은 같아 보여도 한쪽만 --data-dir / 기간을 넣었을 수 있다.

D. 팩터 IC 산출물 경로도 같은 패턴

문서는 case_study_summary.json, 코드는 data/factor_analysis/{factor}/analysis_report.json.

브레인스토밍 — 여섯 줄, 각각 고를 것

각 줄에서 권장만 이번 단계에 넣는다. 나머지는 명시적으로 버린다.

1 · CI

GitHub Actions

A. 기존 워크플로에 pytest만 추가

한 잡이 더 길어진다. 실패 원인이 린트인지 테스트인지 흐려진다.

B. lint / test 잡 분리 ★

지금 YAML을 두 잡으로. uv sync --frozen + 캐시. 테스트는 uv run pytest만. dbt는 데이터가 생기면 다음.

C. 3.11×3.12 매트릭스 + dbt 풀런

웨어하우스 없는 CI에서 dbt run은 실패한다. 매트릭스는 시간만 늘린다.

권장: B. 주석으로 남은 braches 메모도 지운다. README에 CI 배지는 원하면 같이. Spark를 extra로 빼는 일은 설치 개선과 겹치면 후속.

2 · 재현

결과 재현성

A. provenance만 기록 ★

manifest에 git SHA, dirty, 패키지 버전, DuckDB fingerprint (행 수 · max date · 파일 mtime/size). 라이브 yfinance를 비트 동일하게 만들겠다고 약속하지 않는다.

B. 소형 fixture DB를 git에

CI 골든 테스트용으로는 좋지만 용량·라이선스·유지비가 생긴다. dbt 테스트와 묶을 때만 검토.

C. 전체 Parquet 스냅샷 커밋

연구 덤프를 레포에 넣는 일. 하지 않는다.

권장: A를 백테스트·팩터 리포트 양쪽에. 엔진 자체는 합성 데이터 pytest로 “같은 입력이면 같은 CAGR”만 고정한다.

3 · 문서

수치 불일치

A. 지금 DB로 다시 돌려 숫자를 교체

최신이 되지만 2026-07 연구가 사라진다. “그 달의 결과”가 필요한 문서면 안 맞다.

B. 역사로 남기고 출처를 못 박기 ★

숫자는 당시 런의 값으로 유지하되, 재실행하면 달라질 수 있다고 쓰고, 실제 산출물 경로·설정·(가능하면) SHA/fingerprint를 적는다. 다시 돌릴 수 없으면 “재현 불가, 손복사”라고 표시.

C. 표만 지우고 방법만 남긴다

가장 정직하지만 케이스 스터디의 쓸모가 줄어든다.

권장: 먼저 로컬 runs_index.json / 로그와 대조해 A/B/C 가설을 한 번에 판정. 같은 런이면 숫자를 맞추고, 다른 런이면 문서를 분리한다. 그와 별개로 경로·CLI 표기는 코드에 맞춘다 (uv run qseed).

4 · 기록

스냅샷 · 코드 버전

manifest에 넣을 최소 필드 (스키마 1.1 정도로 올림):

필드 왜 만들지 않는 것
code.git_sha / dirty 어떤 커밋이 그 숫자를 냈는지 전체 uv.lock 덤프
code.package_version pyproject 0.1.0 등 모든 transitive 버전 목록
data.db_path, row_count, max_date, bytes 같은 파일이 맞는지 빠르게 확인 테이블 전체 해시 (느리고 이득 적음)
data.markets (이미 있음) 유니버스 티커 전체 리스트를 manifest에

팩터 쪽 analysis_report.json에도 같은 블록을 넣으면 케이스 스터디가 한 형식을 공유한다.

5 · dbt

테스트와 문서

A. schema.yml 테스트만 ★

grain unique + not_null, Market / sector_status accepted_values, source raw_stocks 키 컬럼. 로컬에서 dbt test. CI는 웨어하우스 없이 dbt parse 정도.

B. 싱글톤 fixture DuckDB + CI dbt test

가장 튼튼하지만 fixture를 계속 맞춰야 한다. A가 자리를 잡은 뒤.

C. dbt docs 사이트 호스팅

로컬 엔진에 공개 문서 사이트가 필요 없다.

무거운 fct_stocks__price_factors는 계속 enabled: false. 켜지 않은 모델에 테스트를 잔뜩 달지 않는다.

6 · 설치

Quickstart

A. 문서·Makefile만 고친다 ★

실제 clone URL, 설치 후 make test / uv run qseed --help, “연구하려면 DB가 필요하다”는 한 단락, --build-db --max-stocks 20 스모크. CLI는 uv run qseed로 통일. Docker 포트 설명을 바로잡는다.

B. 샘플 DB를 레포에

클론 즉시 대시보드가 켜지지만 git에 데이터가 생긴다. 후순위.

C. 의존성 extra 분리까지

설치 시간을 줄이는 진짜 지름길이나, 파일/의존성 정리와 같다. 이번 단계 핵심이 아니다.

이후 PR에서 할 일

이 문서 PR의 범위가 아니다. 구현 체크리스트다.

  • CI — lint.yml을 lint/test 잡으로 나누고 uv run pytest를 PR마다 실행. --frozen 캐시.
  • manifest — git SHA/dirty, package version, DuckDB row_count/max_date/size를 백테스트·팩터 리포트에 기록. 단위 테스트 1개.
  • 수치 — 로컬 런과 2026-07 표를 대조해 가설 판정. 문서 숫자·해석을 그에 맞게. 없는 *_summary.json 경로를 실제 산출물로 교체.
  • CLI 표기 — 가이드·케이스 스터디를 uv run qseed로 통일.
  • dbt — 핵심 모델 grain unique/not_null, Market·sector_status accepted_values, raw_stocks 키 컬럼. make dbt-test.
  • quickstart — clone URL, 설치 후 make test, DB 없는 상태와 --max-stocks 스모크 구분, Docker 포트 정정.
